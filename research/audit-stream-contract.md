# Durable audit-stream contract

## Scope and donor decision

This slice implements only the sanitized JSON Lines append sink and the injected input-side ordering guard. It does not capture frames, construct gameplay intents, locate controls, issue native input by itself, read private configuration, open `private/` or `var/`, launch BlueStacks, reconcile lifecycle state, spend resources, send Discord/network traffic, or publish artifacts. Tests use temporary directories, synthetic opaque references, and an injected inert callable.

The pinned donor inventory in `research/scheduler-contract.md` and `research/audit-event-contract.md` assigns safety/audit ownership to the local implementation. BasePilot, CoC_Bot, ClashAutomation, Auto Farmer, the historical Clash Rush tree, keshav-x/coc-bot, and NX-ClashClient have no compatible durable append seam that preserves the local schema-v3 scheduler journal identity, canonical sanitized schema, pre-input suppression, and post-input uncertainty rule. No donor source is copied and no new third-party notice is required.

## Durable append

`DurableAuditStream` accepts a canonical absolute `Path` whose parent already exists and rejects redirected existing files. Opening an existing stream validates every canonical JSONL record and requires contiguous generations beginning at one. Before each append, process-local writers serialize and rescan the stream so independently opened stream objects allocate the next generation rather than retaining a stale value.

Each append constructs an exact `AuditEvent`, writes its bounded canonical record with append semantics, calls `fsync`, then seeks and requires byte-equal tail read-back before returning success. A write, partial write, flush, read-back, or close failure poisons that stream object. No subsequent append through the poisoned object is allowed until a separate future reconciliation contract exists. Existing records are never updated in place.

Stream path and clock capabilities are sealed against ordinary instance shadowing. The input guard snapshots them and prepares an unexposed outcome writer before admitting input; low-level mutation detected after the callback forces `UNCERTAIN` and writes that outcome only to the original snapshotted path. The guard retains pristine append/generation functions across the callback and seals every append dependency used after input, including function code/defaults, the event codec, generation reader, append lock, OS module, syscall functions, and open/seek flags. A shadowed append, module dispatch, in-place function rewrite, or low-level syscall cannot stand in for a durable outcome write; changed append dependencies suppress that write and permit only terminal `UNCERTAIN`. Terminal persistence uses a closure-captured atomic finalizer with closure-captured scheduler validators rather than redispatching through callback-mutable class helpers. Callback completion and the terminal action state are committed together from the persisted `INPUT_STARTED` row, so rebinding the public completion helper cannot create a false in-memory state that strands the authoritative row. The finalizer and every captured scheduler helper are bound by descriptor/function identity, code/defaults, and closure-cell contents; detected mutation is restored to the captured implementation before finalizing only `UNCERTAIN`.

The guard also binds the intent stream immediately after the durable intent to its file identity, length, file modification time, native filesystem change time, parent-directory modification/change times, and SHA-256 content digest. On Windows the native change time comes from handle-bound `FileBasicInfo.ChangeTime`, which `os.utime` cannot restore; other platforms use the descriptor change time. The sealing function binds its stat/open/hash/change-time operations as function defaults, and the native change-time reader similarly binds its platform, handle conversion, Win32 query, structure, and error operations. The input guard seals both functions' identities, code objects, and default tuples plus the native query's ABI and error hook before input, rechecks that boundary before invoking it afterward, and allows altered dispatch to finalize only `UNCERTAIN`. The same file evidence must remain stable while each seal is read. Unlink, replacement, transient or lasting rename, transient or lasting truncation, transient rewrite/restore, and same-size canonical rewrites during the input callback can never produce a confirmed result. The scheduler database path is snapshotted before input; if the callback closes the injected store after `INPUT_STARTED`, the guard reopens that exact database and atomically finalizes the action `UNCERTAIN`, preserving restart non-replayability.

The current runtime contract has one process owning the host-wide lifecycle/input lease. The process-local append lock is not presented as a cross-process lease; later composition must keep the stream beneath that already-required single-writer ownership boundary.

## Input ordering

`execute_audited_input` accepts an already planned exact scheduler action and an injected callable. It first durably transitions the scheduler action to `INTENT_RECORDED`, then requires a durable `ACTION_INTENT` append. Any failure before `INPUT_STARTED` returns `SUPPRESSED` and never invokes the callable.

After the scheduler has durably recorded `INPUT_STARTED`, the callable may return only the closed `InputResult.SUCCEEDED` or `InputResult.FAILED` value. Exceptions, base exceptions, or any other result are uncertain. A canonical `ACTION_OUTCOME` record is then required. If this post-input append fails for any reason, the scheduler action is finalized as `UNCERTAIN`; it is therefore non-replayable across restart. Successful and failed closed results finalize as `CONFIRMED` and `FAILED` only after their corresponding outcome append succeeds.

The terminal scheduler action and pending lane continue to commit atomically through the existing schema-v3 `SQLiteJobStore.finalize_action` boundary. This slice does not add an executor, target vocabulary, spending authority, or replay path.
