# Standing development workflow

This is the detailed policy referenced by the sole project loader, [.hermes.md](../../.hermes.md).
The owner's governance adoption decision controls; the four reset drafts and the
reconciliation package are evidence, not executable prompts. Their old option 5C
label and numeric currency-budget recommendations are superseded by the owner's
[non-premium currency decision](../product-policy/spending.md). Historical receipts
remain unchanged. This documentation candidate grants no implementation milestone,
native action, capture, installation, provider egress, or live run.

## 1A — Standing offline autonomy

Inside an explicitly adopted, bounded offline milestone, Hermes owns routine
implementation mechanics, directly coupled edits, tests, fixtures, debugging,
harmless disposable test harnesses, and one normal corrective pass. Record
consequential decisions and tradeoffs; do not ask again about routine mechanics.
This continuity rule does not start a milestone, override a hold, or automatically
start the next backlog item.

Owner input is required only for undecided product behavior; material architecture
or invariant changes; live/external authority; privilege/system changes; new
production dependencies/services; a second failure of the same seam; or evidence
contradicting the approved architecture. Ask for the smallest missing decision.
Continue independent work only where it remains authorized.

## Delivery and evidence

Before work, reconcile the actual local branch/commit/tree, staged and unstaged
changes, current gate and attached decision, installed versus source entrypoint,
profile scope, and latest review/native evidence. Preserve others' work. Remote
main, a draft, or an old conversation cannot establish current local state.

Trace pinned BasePilot, then CoC_Bot and the relevant comparison donor before a
substantial capability change. Follow complete reachable callers/helpers/assets/
tests and licensing; adapt the largest compatible behavior through thin boundaries.
Reject unsafe transport, blind fallback and unlicensed copying. Reuse a comparison
until evidence or assumptions change. Do not replace working code just because its
history was not test-first; characterize it before testing the intended change.

For a defect, trace the real source/installed path, reproduce with already permitted
evidence, form one hypothesis, establish behavioral RED or honest characterization,
make the smallest complete fix, then verify offline. Never fabricate pixels/counts,
RED history or results; weaken thresholds to pass; suppress failures; or mock away
the production seam being tested. Separate fitted observations, derived negatives,
synthetic boundaries and held-out/dynamic evidence.

Use available systematic-debugging and TDD methods with actual tool schemas. No
installed-Superpowers assumption or plugin installation follows from this workflow.
Use one implementer per mutable lane, explicit isolated worktrees/branches, and one
continuation controller. Static research/review or disjoint implementation may run
independently only with explicit context and ownership. Worktrees do not isolate the
Windows cursor: exactly one host-wide game-input/lifecycle owner is permitted, and
only under separately current authority.

Contract → donor trace → behavioral RED/characterization → complete adaptation →
focused verification → canonical/clean-export checks when applicable → immutable
exact-tree handoff → one substantive whole-feature review → at most one normal
corrective pass. Second same-seam failure means REASSESS and owner input, not a new
card, hypothesis, session or renamed successor resetting the limit. Every production
change after PASS requires focused review of its new tree before promotion. Serious
correctness, authority, privacy, state-truth or ownership defects block promotion;
unrelated preferences go to the backlog. Review caps never waive defects.

## 3A — Image privacy and provider policy

Preserve current privacy defaults: grant no additional image/provider egress, no
provider change or fallback authorization, and no new full-frame retention exception.
Full game frames remain memory-only under standing defaults; private game evidence,
account data, calibration, credentials and runtime state remain in approved ignored
`private/` or `var/` roots, never tracked/public material. Only already approved
narrow-crop retention and separately reviewed, exactly scoped historical exceptions
retain their own boundaries; citing them cannot activate or broaden them here.
Synthetic evidence is never native evidence.

Any future provider/full-frame exception requires a separate owner decision covering
exact provider/model/route/destination, artifact scope, access, retention/deletion,
Hermes image caches/transcripts, backups and remote copies. Local deletion does not
prove remote deletion. Configured routing is neither consent nor proof of pixel
receipt. The historical startup-debug exception is unresolved in scope and cannot
be used to infer ordinary retention. No new capture or private-image upload is
permitted by this adoption.

## 4A — Future live development

No live authority is granted now. A later live-development envelope must be explicit,
finite, exact-candidate/profile/instance bound, revocable, independently reviewed,
and separate from standing workflow law. Use the separate [inactive template](live-development-envelope-template.md).
All bindings remain unset until a future explicit owner grant; storing, attaching,
sending, reviewing or integrating that template activates nothing. An offline PASS,
accepted currency class, task completion or goal cannot substitute for admission.

Stop new input/admission on identity/window uncertainty, unproved button/key release
or owned shutdown, prohibited action/spend, expired/exhausted authority, or
unreconciled external state. Never forge a grant, force READY or replay an uncertain
transaction. Cleanup uses only exact existing ownership/cleanup authority; failed
proof blocks the next attempt. A future retry needs settled prior lifecycle, an
independently reviewed current tree and explicit remaining authority. Goals, repairs
and restarts cannot reset the cumulative ledger. Recurring gates must be offline,
not repeated capture, attacks or other external side effects.

## Completion and navigation

Acceptance uses the installed runner without Hermes choosing gameplay actions or
rescuing it. Label exploratory/assisted attempts. Report implemented, offline-tested,
live-observed and accepted separately, with exact candidate/profile identity,
actual commands/results, every attempt including failures, review verdict and
remaining blockers. Historical receipts remain byte-honest; policy changes are not
permission to silently rewrite them. Stop at the adopted milestone.
